01 Processing abstraction

Wrap any tool as a UNode

A UNode is a thin, versioned layer between a tool and the framework. It declares what goes in and what comes out, builds the command line, and leaves IO, secrets and metadata to urgap. No glue code — your tool stays your tool.

  • Typed contracts. Inputs and outputs are declared as uftypes with min/max counts, so mismatched wiring fails before anything runs.
  • One lifecycle. Every node runs preflight → execute → postflight, with checks for third-party tools like Java, R or .NET up front.
  • Pinned versions. Tool versions and wrapper versions are explicit and become part of every output's identity.
  • Container-ready. The same node runs in-process, as a microservice, or behind a message bus.

02 Provenance as Code

The file name is the provenance

In urgap, nobody picks output names. Each name is a deterministic digest of the tool and its version, the parameters that change results, and the signatures of the inputs. Lineage isn't bolted on afterwards — it's encoded where the data lives.

Try it — change a parameter

Hashes here are computed in your browser for illustration; urgap uses MD5 or blake2 over the sorted parameter JSON.

Output object name

FilterTabularToCSV_1_0_0_w1_…/7d2a91c04e…be13_1_of_1.any.csv

  1. Resource — node name & tool version
  2. Parameters — only those that affect results
  3. Inputs — digest of input ucfs signatures
  4. Type — output uftype, plus n_of_N

Same inputs, same parameters → same name → skipped.

ucfs — an ISBN for files

<object_name>@<md5>. The same title can sit in many bookstores and keep one identifier; the same file can sit in many clouds and stay one asset.

Identity ≠ location

A UFile is a URI: scheme://location#object_name. The scheme picks the backend, the fragment is the identity. Move data without breaking anything.

FAIR by design

Every asset carries its own lineage. Files become self-describing — findable, reusable and governable without extra paperwork.

03 Agent-ready

Agent-ready by design

Every UNode can be served as an MCP tool. An agent calls STAR, kallisto or a CSV filter the same way a pipeline does — and because it goes through the same Provenance-as-Code path, everything it does is versioned, traceable and reproducible. Ask twice, compute once.

agent session · urgap MCP

  2. ensure_urgap_uri_format["gcs://my-project/raw"] → ok
  3. list_container_itemspattern=".*\.csv$" → 3 files
  4. generate_workflow_id→ u_brisk-otter-sorts-amber-river

  7. Run that again for the report.
  8. FilterTabularToCSV_1_0_0outputs exist → skipped

Nodes become tools

Serve nodes over REST and MCP side by side. Tool names are derived from the node, e.g. FilterTabularToCSV_1_0_0.

uctl run upi-server -n FilterTabularToCSV:1.0.0 --mcp-port 8765

Your docs are the prompt

A node's docstring and parameter_examples become the tool description, so the model learns the exact parameter format from the wrapper itself.

Built-in helper tools

list_container_items, generate_workflow_id, ensure_urgap_uri_format and storage-URI builders for GCS and Azure. MCP prompts teach the urun_dict format; resource templates build storage URIs.

uctl run mcp-server -p 8000

Agent-to-agent

The a2a_caller node calls other A2A agents, so an agent hop is just another versioned, traceable step in your pipeline.

Governance for free

Agent runs get deterministic output names, rerun skipping, lineage tags and UMeta records — exactly like scheduled pipelines. You can audit what an agent did, and why.

04 Smart rerun

Smart reruns, everywhere

Before a node runs, urgap already knows the names its outputs will have. If they exist — anywhere in your storage, from anyone's run — the step is skipped. Change a parameter and only that step and its descendants run.

  • Fork freely. Define a pipeline without knowing what already exists; finished work is reused.
  • Compare methods cheaply. Swap one node, keep the rest of the graph — competing approaches run on identical inputs.
  • Operational parameters stay out. Thread counts and similar are listed in parameters_not_triggering_rerun.
  • Force when you mean it. force=True reruns anyway. You used the Force.

05 Data abstraction

One file abstraction, any storage

A UFile is a URI. The same node code reads from a laptop and writes to a bucket — the scheme decides how to talk to storage. Access .path and the file is downloaded to scratch; call rebase() and it moves, identity intact.

azure://account.blob.core.windows.net/raw?uftype=.any.csv#runs/BSA1.csv

scheme → IO backend location → where it lives uftype → what it is fragment → identity
  • file://Local file system
  • https://Any web endpoint
  • azure://Azure Blob & Data Lake
  • az-smb://Azure file shares
  • samba://SMB shares
  • gcs://Google Cloud Storage
  • github://Files in a GitHub repo
  • git://Any git remote

Tags everywhere

Checksums and lineage live in object tags. Backends without native tags get a sidecar .tag JSON.

Secrets, handled

Credentials resolve from Azure Key Vault, GCP Secret Manager or environment variables — never hard-coded in nodes.

Parallel IO

UFileList downloads in parallel, filters by uftype or tags, and rebases whole sets in one call.

06 Metadata

Lineage you can query

Every output carries its parents and a compressed provenance graph in its tags. Run details — configs, timings, inputs, outputs, user metadata — are recorded automatically in UMeta, so you can answer "where did this come from?" from the command line.

  • UMeta backends: SQLite by default, PostgreSQL or Cloud SQL when you share.
  • Workflow IDs: every run is grouped under a readable wid.
  • Your context too: attach a user_dict such as experiment ID or operator.

08 Operations

Nodes as services, observable by default

One command turns any node into a FastAPI microservice with health probes. Point a pipeline at it with remote_url and the run happens there — same inputs, same names, same lineage.

  • Kubernetes-friendly: /livez and /readyz out of the box.
  • OpenTelemetry: spans and counters for every run, exported via OTLP, Azure Monitor or console.
  • Standardised logs: every node logs the same way, so debugging looks the same everywhere.
